# D2.1 — Bioenergetic-first catalog and migration notes

Version: 1.1.0

## What this package changes

- Adds a catalog that makes the bioenergetic framework the primary interpretive lens.
- Keeps physiology as a distinct mechanistic layer.
- Keeps mainstream clinical evidence as a separate comparison layer, not a footnote.
- Adds explicit critical appraisal and safety layers.
- Preserves all ten existing dataset IDs and file paths.
- Adds no unverified scientific claims and does not modify participant data.

## Important repository finding

When the repository was inspected for this revision, all ten tracked dataset files contained empty `records` arrays and the manifest recorded zero records for each dataset. Therefore this D2.1 package does not pretend that the earlier proposed starter records are present in the GitHub repository. If those records exist in a local ZIP or another branch, merge them deliberately after checking source details and schema compatibility.

## Upload locations

Copy these files into the repository:

- `docs/phase-d/D1.1-bioenergetic-first-architecture.md`
- `docs/phase-d/D1.1-claim-and-evidence-policy.md`

Keep the existing `knowledge/manifest.json`, dataset paths, and original v1 schema unchanged for now. The catalog is an additive architecture file; the live app and current validator do not consume it yet.

## Record migration rules

For each existing record, assign:
- `framework`: one of `bioenergetic_primary`, `physiology`, `mainstream_comparative`, `safety`, `cross_framework`.
- `theoretical_status`: one of `established_mechanism`, `supported_model`, `contested_model`, `historical_hypothesis`, `speculative_hypothesis`, `not_applicable`.

Do not assign `bioenergetic_primary` merely because a record mentions metabolism or energy. Use it when the record explicitly represents a bioenergetic model or hypothesis. For example, a historical presentation of Ling's association-induction hypothesis may be tagged `bioenergetic_primary` plus `historical_hypothesis`; this does not mean the model is clinically established.

## Validation warning

The current `scripts/validate_knowledge.py` checks manifest hashes and dataset envelopes, but does not validate individual records against JSON Schema. Do not claim schema validation has passed until a record-level validator is added and run.

## Next phase

D3 can design the assessment output contract and UI presentation, but it should not generate participant-specific interpretations until the data sources, record validation, and safety handling are implemented.
