## Design decision
The questionnaire should be structured-first. Use single-select, multi-select, numeric values with units, measurements, time, duration, frequency, and repeatable structured records. Keep free text only as an optional residual note or for genuinely unclassifiable context.

Do not convert every textarea into one giant multiple-choice question. Split compound concepts into separate measurable fields. Example: replace a free-text food-trigger answer with repeated records containing food, amount, symptom, onset latency, duration, and reproducibility. Keep a note field for details that do not fit the schema.

## Registry rules
1. IDs are immutable storage identifiers.
2. Labels may change only when the meaning and recall period remain equivalent.
3. Changes to construct, timeframe, unit, method, answer scale, or interpretation require a new ID or explicit versioned migration.
4. Missing is not zero, no, normal, or negative.
5. Retired questions remain readable in old profiles.
6. Option values are stable machine codes. Never repurpose an existing code.
7. Numeric fields require units, precision, validation bounds, and an indication of whether values are measured or estimated.
8. Repeated measurements require timestamps and method/site metadata.
9. Subjective ratings remain subjective; do not treat ordinal categories as objective physiological quantities.
10. Preserve raw answers alongside normalized values so transformations remain auditable.

## High-priority structured conversions
- `height`: numeric centimetres; preserve legacy string.
- `health_conditions`: coded condition list; optional diagnosis details and date.
- `family_history`: relationship, condition code, age of onset if known.
- `medications`: repeatable records with name, dose, unit, route, frequency, start/stop dates, prescribed status.
- `baseline_goal`, `priority_goal`, `success_definition`: goal domain, metric, baseline, target, timeframe; optional note.
- `morning_temp`: repeated measurement records, not one "typical" number; include value, unit, site/device, timestamp, rest period.
- `morning_pulse`: repeated measurement records with timestamp, posture, rest period, method.
- `food_reaction`: food code, amount, symptom code, onset latency, duration, recurrence.
- `urinary`: split into distinct symptoms (urgency, frequency, weak stream, pain, nocturia, blood) rather than one severity answer.
- `injuries`: body site, type, onset, current status, severity, functional limitation.
- `cardio`: activity type, sessions/week, minutes/session, intensity.
- `food_log`: repeatable food records: item, amount, unit, preparation, time, confidence.
- `meal_times`: repeatable meal events with local timestamp.
- `dairy_other`, `starch_day`, `fat_sources`, `vegetables`, `protein_sources`, `nuts_seeds`: item code + quantity + unit + preparation/frequency.
- `juice_day`, `gelatin`, `legumes`, `alcohol_nutrition`: quantity + unit + explicit time window.
- `caffeine`: beverage, serving size, estimated caffeine amount, timestamp.
- `temperature_env`: numeric temperature + unit + room/time context.
- `stress_sources`, `life_domains`, `barriers`: multi-select categories plus optional note; do not turn narrative into a diagnostic score.
- `sunlight`: duration plus timing relative to waking and whether outdoors/through glass.
- `supp_food`: coded restriction reason and excluded food groups, with optional notes.

## Analytical safeguards
- Never convert a subjective option to a numeric score unless the scale has a defensible measurement model.
- Do not infer causation from co-occurrence.
- Do not treat self-estimated food intake as measured nutrient data.
- Do not infer endocrine status from libido, temperature, pulse, or symptom clusters alone.
- Ray Peat/Ling-inspired interpretations may be the primary explanatory layer, but every claim must carry an evidence status. Established physiology, supported hypotheses, contested claims, and speculation must remain distinct.
- Conventional clinical safety review remains a separate section and can override any interpretive narrative when urgent warning signs are present.

## Implementation sequence
1. Add a test asserting every active questionnaire ID exists in this registry.
2. Add full exact labels, options, units, ranges, recall windows, and question-level metadata from the live source.
3. Add structured companion fields with new IDs. Do not mutate old fields in place.
4. Add migration code that preserves legacy values and never deletes unknown keys.
5. Update D3 analyzer to consume normalized structured values only; keep original values for traceability.
6. Add tests for old profiles, missing values, option aliases, unknown keys, and changed question semantics.

## Known limitations of this first registry
This inventory captures IDs and legacy answer types, but does not yet freeze every exact label and option code. Before the UI is changed, the registry must be enriched with exact live labels, option values, units, ranges, recall periods, and required/optional status. The current app contains some mixed-construct questions and fields with ambiguous units; those must be corrected explicitly rather than guessed.
