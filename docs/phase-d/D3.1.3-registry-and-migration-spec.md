# D3.1.3 — Assessment registry, redesign and migration specification

Status: design release; no live UI or stored profile changes.

## Release scope

This release consolidates three connected deliverables:
1. An ID-first inventory of the assessment fields grouped by the current 11 questionnaire modules.
2. A revised questionnaire information architecture and field-quality specification.
3. A backward-compatible migration model for existing `bioenergetic_profile_v1` browser profiles.

The registry includes 178 IDs: the 166-field baseline inventory plus 12 later physical-performance fields. It deliberately does not fabricate exact labels, control types, or select options. Those values must be synchronized from the exact deployed `app/index.html` before implementation. This is a hard gate, not a cosmetic task.

## Non-negotiable compatibility rules

- `id` is the canonical key. Never rename or repurpose an existing ID in place.
- A wording-only change may retain an ID only when the construct, timeframe, response meaning, and unit remain the same.
- A semantic change requires a new ID and an explicit migration mapping.
- New questions in an older profile remain unanswered. Never infer `false`, zero, normal, or absence.
- Retired questions remain readable in historical profiles and exports.
- Unknown assessment keys must survive import, export, and save cycles.
- Option values are stable machine values. Display labels can change only when the underlying meaning does not.
- Numeric fields require an explicit unit, valid range where defensible, precision, and provenance.
- Repeated measurements require timestamp, method/site, and context; a single profile field is not a time series.
- Preserve raw legacy values alongside any normalized representation until migration has been validated.
- Do not silently map free text into a diagnosis, symptom severity, or binary state.

## Questionnaire architecture

### A. Identity and clinical context
Keep age, sex assigned at birth, height, weight, diagnoses, family history, medications, recent illness, nicotine, alcohol, and goals distinct. Diagnoses, suspected conditions, symptoms, and family history must not share a single field. Medication records should eventually become repeatable entries with name, dose, route, frequency, start/stop dates, indication, prescriber, and source.

### B. Body measurements
Weight, waist, hip, and body-fat estimates need value, unit, date/time, method/device, and measured-versus-estimated status. Body-image confidence is subjective context, not a measurement and not a diagnostic score.

### C. Thermoregulation and circulation
Separate waking temperature and pulse as dated repeated observations from general cold/heat tolerance and fatigue questions. Every reading should carry:
- local timestamp and timezone,
- value and unit,
- measurement site/device,
- rest/activity state,
- time since waking and food/caffeine/exercise where relevant,
- symptoms and environmental context,
- measured, estimated, or recalled provenance.

Do not compare oral, axillary, ear, and forehead readings as if interchangeable. Do not collapse measurements from different sites into one unqualified average.

### D. Digestion and meal response
Break compound urinary/digestive/reaction prompts into discrete symptoms where useful. For food reactions, use repeatable events: food, quantity, preparation, time eaten, symptom, onset latency, duration, reproducibility, and confounders. Bristol stool categories remain categorical. Do not convert ordinal choices to an interval scale without validation.

### E. Sexual and reproductive health
Keep optionality and prefer-not-to-answer explicit. Separate urinary stream, urgency, frequency, pain, nocturia, and incomplete emptying rather than treating the current `urinary` field as a single severity scale. Use a distinct applicable/not-applicable state; do not infer from sex assigned at birth.

### F. Sleep and circadian context
Separate habitual schedule from actual daily sleep records. Record actual bedtime, estimated sleep onset, awakenings, final waking, out-of-bed time, naps, and confidence. Light exposure should include timing and duration, not just frequency. Snoring or witnessed breathing pauses are observations, not a diagnosis.

### G. Cognition and mood
Keep self-reported experience separate from clinical diagnoses. Use clear recall windows and neutral wording. Do not generate psychiatric diagnosis, risk score, or causal attribution from these fields.

### H. Physical performance
Distinguish training exposure from test outcomes. Performance tests require protocol, equipment, date, warm-up, surface, technique, effort, and injury status. A test without repeatable protocol is descriptive only. Never encourage maximal testing when unsafe.

### I. Nutrition
Use repeatable food-log entries and explicit quantities. Distinguish cooked from dry weights, edible portion, preparation, brand/fortification where material, and estimate confidence. Intake totals must state source and uncertainty. Avoid false precision from guessed calories/macros. Dietary pattern labels are not nutrient measurements.

### J. Environment and lifestyle
Capture schedule, daylight, room temperature, sedentary time, outdoor exposure, stressors, and social context as reported context. Do not infer pathology from social status, goals, or perceived control.

### K. Goals and agency
These fields are planning context only. They must not feed disease inference, personality classification, or a learned-helplessness score. Keep goals observable and user-defined.

## Field-quality requirements

Each active registry record must ultimately include:
- exact source label and control type;
- exact select option values and labels;
- module and display order;
- construct definition;
- recall window;
- unit and precision for numeric/time values;
- allowed range and validation rationale;
- missingness behavior;
- provenance and confidence semantics;
- sensitivity classification and consent behavior;
- whether the field is repeated, categorical, numeric, or free text;
- migration and deprecation metadata.

## Structured target data model

Use additive structures; do not replace the current assessment object in one destructive migration.

  "schemaVersion": "2.0.0",
  "assessment": {
    "legacy": {"<existing-id>": "raw legacy value"},
    "answers": {
      "<question-id>": {
        "value": null,
        "status": "not_answered",
        "recordedAt": null,
        "recallWindow": null,

  },

    }],

This is a target contract, not a claim that the current app already stores this structure. Keep current `db.logs`, `db.healthData.daily`, `db.supplements`, `db.supplementSchedules`, and `db.supplementAdherence` intact during the first migration.

## Migration stages

1. **Inventory:** fetch exact deployed source; populate exact labels/types/options; detect duplicate IDs and IDs missing from registry.
2. **Shadow schema:** add `schemaVersion` and `assessment.legacy` without changing rendering or deleting old keys.
3. **Read compatibility:** readers prefer structured answer when present; otherwise read legacy key. Do not write back a guessed normalized value.
4. **Dual write:** only for fields with approved mappings; write raw legacy value and structured value together.
5. **Validation:** test import/export round trips, old backups, unknown keys, missing values, malformed values, and repeated imports.
6. **Cutover:** only after parity tests; preserve legacy values for at least one full release cycle.
7. **Retirement:** remove legacy reads only after documented user-facing migration and backup compatibility review.

## Safety and evidence boundaries

The bioenergetic interpretation layer remains the primary explanatory lens, but it must label claims as established mechanism, supported hypothesis, contested claim, or speculation. For every interpretation include plausible alternatives, confounders, and what observation would weaken the hypothesis. Mainstream clinical comparison remains a separate section. Safety escalation remains a separate section and takes priority when urgent symptoms are present. The questionnaire itself must not diagnose, rank disease probabilities, or prescribe treatment.

## Implementation gate

Do not modify `app/index.html` until:
- exact source labels/options are synchronized;
- every field has a stable registry entry;
- the target data contract passes schema validation;
- migration tests pass against real synthetic copies of old backups;
- a rollback path is documented.
